# v1.4.9 P4-B-D2 Full Execution 集成验收

本次以 `coding-man-wang/fe-agent` 的 `main@d53834a` 为代码基线，将真实候选消费、A/B 对照、模型用量计量、闭环验证与安全回退作为一个完整交付阶段。实现已从 Preview 扩展到显式的隔离 Active 实验；**生产 Active 默认仍关闭**。本文区分代码已实现与实验已验收，不把单测、候选校验或字符减少当作真实 A/B 成功。

## 已实现的执行链路

普通入口继续使用 Baseline。`--context-guarded-preview` 校验候选但只向 Coding Agent 交付 Baseline；`--context-guarded-active` 只在隔离 Benchmark 中允许 `CASE-006 / TASK-002` 消费通过全部门禁的候选；`--context-ab` 固定一份 Prepared Input，顺序运行独立的 Baseline 与 Active，再生成对照验收报告。所有实验报告的 `production_ready` 保持 `false`，A/B 通过也不会改变生产开关。

```text
既有 passed Prepared Input + Case/Revision/Canary 准入
  -> 当前任务 committed snapshot / 一次 Retrieval / Fresh Change Surface
  -> 同一最终构建器：Resolved Context -> Obligation Evidence -> Verification Strategy
  -> 冻结输入及源码证据 -> D1 Observer -> D2-B Preview -> 共享 C1 验证
  -> 持久化审计 -> 再次检查完整快照
       Preview：返回报告，模型继续使用 Baseline
       显式 Active：仅合格 TASK-002 返回已验证候选
       fallback：返回仍有效的原始 Baseline
       blocked：不返回可消费 Bundle，终止任务
  -> prepare_messages -> 消费前再次复核
  -> Coding / Patch / Verification / Scope / Obligation / Completion
  -> Hidden Acceptance / 最终评估 / A/B 比较
```

Baseline、Trial 和 Active 共用 `_build_final_execution_context`。共享 C1 验证使用真实 `GuardedContextPolicyConsumer`，不另写过滤算法；每个候选只运行一次 Consumer，不为了 Active 再运行一遍 Trial。重建使用当前 Selection、Surface、Index 与 Task Plan，不重复 Retrieval，不重新授予文件写权限。原来的 `run_guarded_active_trial()` 与 Preview 公开接口仍只返回报告。

Active 接口返回 `GuardedActiveResult`：`active` 携带已验证候选，`fallback` 携带原 Baseline，`blocked` 的 Bundle 为 `None`。交付前验证保留文件内容、顺序和 Symbol 证据一致，除 Context 与预算外的元数据不变；已有必需证据不能缺失，仅显式 `create_files` 中允许新建的目标可以暂不存在。`assert_fresh()` 在实际模型消费前重新检查原始完整证据及交付 Bundle，覆盖已经从候选中移除的源文件。

`applied=true` 表示本次实验接受并交付了候选，不代表 Patch、任务功能或整个 A/B 已成功。`active_execution_enabled=true` 也仅描述本次受限实验，不是生产配置。其他 Task 或后续不同 Revision 不能继承 TASK-002 的资格，继续使用有效 Baseline。

## 准入与安全回退

| 条件 | 行为 |
| --- | --- |
| Preflight 拒绝、模式冲突、没有既有 passed Prepared Input | CLI 退出，不启动该受控 Full Execution |
| 非白名单 Task、批准 Revision 不匹配、未显式启用实验 | 不运行候选观察，记录 fallback，使用有效 Baseline |
| 无有效删除、建议删除受保护证据、候选重排或保留内容/元数据变化 | 拒绝候选；完整快照有效时使用 Baseline |
| Observer 超时或异常、候选重建失败 | 无法证明候选安全则拒绝；只有 Baseline 仍可验证时才回退。Baseline 重建失败可直接 blocked |
| 必需已有证据不在 Baseline，或非批准新建目标缺失 | blocked；集合交集不能证明证据完整 |
| 审计缺失、拒绝、抛错或返回未等待的异步操作 | 不交付候选；完整快照有效时回退 Baseline |
| 源码、Revision、Selection、Baseline、Surface、Obligation 清单或候选发生变化 | blocked；不能使用旧 Baseline 掩盖变化 |
| 消息准备后证据或 Bundle 变化 | 在模型消费前阻断，记录失败并尝试追加阻断审计 |

快照覆盖 Selection、最终 Context、Surface/Strategy/Obligation 源文件，以及尚未创建的批准目标；实际 Git HEAD 与 committed worktree 的 tracked/untracked 状态也必须保持干净，以覆盖最终构建器读取的其他文件。早期拒绝、异常及审计失败同样经过最终检查。审计通过同步追加、flush 与 fsync 持久化，只记录路径、状态、用量和摘要，不保存源码、Prompt、输出正文或 API Key。

不传入实验参数即使用普通 Baseline 入口。出现源码变化时应从正确 Revision 重启执行，不能关掉实验后继续消费旧上下文。测试不得通过去除路径限制、源码哈希、Scope Guard 或 Completion Gate 来规避失败。

## A/B 冻结边界与验收

两个 arm 使用同一 Case、初始 Benchmark Revision、Prepared Input 和上游结构化记录，但有不同 run ID、隔离工作区及 task workspace ID。Baseline 没有通过完整执行评估时停止，不启动 Active；Active 开始前重新检查准入和冻结身份，输入变化则输出失败报告。

`context_experiment_identity` 记录以下摘要：

- Case 内容及批准的目标仓库 Revision。
- Prepared Input，以及 baseline 的 Requirement、Technical Spec、Task Plan、Project Context。
- 对应 Harness run 的 `artifacts/*/*.json` 文件内容。
- LLM、Embedding、Rerank 的模型 ID 与 Base URL，加上本次实现标记；不写入密钥。
- 准入读取的 Canary 原始字节 SHA256。

这些是代码实际绑定的字段，不代表冻结了提供方内部模型版本、服务端路由或随机性；A/B 也不承诺相同输出文本。Active 结束后再次读取 Canary 并复核准入及冻结身份，防止把发生变化的输入当作同一实验。

比较器同时检查独立运行与工作区、arm 模式、Task Plan、Oracle、最终评估、Hidden Acceptance、验证和修改范围，并要求 TASK-002 确实使用 `active` 候选。其他任务不得出现 Active 应用。候选必须有非空、与批准建议一致的文件删除，字符数下降，保留必需证据，且四项质量标记全部通过：`mandatory_context_complete`、`retained_symbol_evidence`、`metadata_unchanged`、`scope_unchanged`。

| 对照结果 | 含义 |
| --- | --- |
| `passed` | 所有质量/身份/隔离门禁通过，实际 LLM usage 完整可比，总 Token 没有回归 |
| `inconclusive` | 质量门禁通过，但 usage 不完整或不可比，不能确认完整开销验收 |
| `failed` | 质量/安全/身份/隔离不通过、实际未消费 Active、没有有效压缩，或可比总 Token 增加 |

`fallback` 即使完成了业务任务，也不能计为 Active 优化成功。Token 节省不能抵消功能、安全或证据退化；文件数、字符数和真实 Token 分开报告。零 Token 增长属于无回归，不应宣传为正向节省。

### 计量范围

`MeteredLLM` 位于 `RetryingLLM` 内层，记录每一次真实 LLM 提供方尝试，包括重试、失败和取消，并按 task/run 保存调用次数、错误类型、模型、Prompt/Completion/总 Token 与累计调用耗时。累计耗时是提供方调用时间之和，不是整段运行的墙钟时间。

本次 usage 范围明确为 `llm_provider_attempts`，**不包含 Embedding 与 Rerank 请求，也不是端到端总费用**。不根据字符数估算 Token。失败、未完成、缺失或不一致的 usage 会使完整 totals 不可用；`known_*` 仅表示已知部分，不能作为完整成本。比较器要求实际模型集合一致、两端 usage 完整且其他身份/隔离条件可比，再计算 `llm_tokens_saved`。

## 执行命令与报告

以下命令与 `apps.agent_cli.benchmark_v1_1_run` 的实际参数一致。`$revision` 必须是 **Benchmark 目标仓库** 的已批准版本，不是 FE-Agent 的代码版本；该版本需与 Case、Canary 和 Prepared Input 匹配。目标仓库还需具有既有可用的 Node/npm 验证依赖，模型及诊断服务配置使用现有项目环境。

```powershell
$benchmarkRepository = 'D:\project\fe-agent-benchmark-web'
$revision = git -C $benchmarkRepository rev-parse HEAD

# 只做准入检查，不调用模型或运行 Full Execution。
uv run python -m apps.agent_cli.benchmark_v1_1_run --case-id CASE-006 --benchmark-repository $benchmarkRepository --context-active-preflight --active-task-id TASK-002 --approved-revision $revision

# 单次真实受控 Active；Patch、验证和 Commit 发生在隔离 Benchmark 工作区。
uv run python -m apps.agent_cli.benchmark_v1_1_run --case-id CASE-006 --benchmark-repository $benchmarkRepository --context-guarded-active --active-task-id TASK-002 --approved-revision $revision

# 完整 Baseline/Active 对照：自行执行两个 arm，不需要先运行上一条命令。
uv run python -m apps.agent_cli.benchmark_v1_1_run --case-id CASE-006 --benchmark-repository $benchmarkRepository --context-ab --active-task-id TASK-002 --approved-revision $revision
```

如需观察而不交付候选，把上面的模式参数替换为 `--context-guarded-preview`。`--context-active-preflight`、`--context-shadow`、`--context-guarded-preview`、`--context-guarded-active` 和 `--context-ab` 互斥；受控实验不能同时使用 `--refresh-upstream`。已有 Canary 位于 `var/canary/context_policy_v1_4_9.json`，这些入口不会自动重建 Canary。

每个 Full Execution run 保存任务状态、实际上下文文件、Verification/Completion/Hidden Acceptance 和运行评估，以及 `context_experiment_identity`、task/run `model_usage`。实验审计文件为 `context_guarded_active.jsonl`，Preview 为 `context_guarded_preview.jsonl`；对应任务记录保存同名报告，`context_shadow_message_sha256` 绑定实际消息摘要。`baseline_bundle_sha256` 指向原始完整 Bundle，`consumed_bundle_sha256` 指向实际交付的 Bundle。

A/B 总报告以 JSON 写入 `.fe-agent/benchmark/full_execution/ab/`，CLI 输出 `ab_report=...`。正常完成比较时保留两个 run ID、逐项门禁、失败原因、上下文/真实 usage/实际修改范围和生产关闭状态；Baseline 初始化或业务失败、两组之间准入改变、Active 初始化失败时保存失败原因与已有 run ID。最初的 Preflight 拒绝会输出准入报告并退出，不创建 A/B 运行。A/B `failed` 或 `inconclusive` 均返回非零退出码。单次 Active 如果只执行了 Baseline 回退，同样返回非零；候选已应用时还会重新检查 Canary 和冻结输入。单次 Active 成功不等于两组 A/B 已验收。
